# FSP-ENCYCLOPEDIA-RESEARCH-FRONTIER-1

## Canonical/Core vs Comparator vs Experimental Research, Frontier Card Schema, Promotion-to-Core Gate, Cross-Linking Rules, Claim Ceilings, and REOPEN

**Status:** ENCYCLOPEDIA CONSTITUTIONAL EXTENSION — VERSION 1  
**Role:** Establish a research-frontier layer for the FSP Encyclopedia that can host provisional inquiry without silently mutating canonical FSP.  
**Primary purpose:** Preserve epistemic status, provenance, and developmental history while allowing the Encyclopedia to display not only settled architecture but also open research dependencies.  
**Primary claim ceiling:** This document specifies how developing research should be represented and governed inside the Encyclopedia. It does not make any Frontier program canonical, prove any candidate Firewall, or revise the current Core/JTS architecture merely by hosting it.

---

# 1. Why the Encyclopedia Needs a Research Frontier

The FSP Encyclopedia has developed from a public reader into a connective architecture linking:

- prose;
- cases;
- Concepts;
- Tools;
- Firewalls;
- state transitions;
- controlled probes;
- source ledgers;
- claim ceilings;
- comparisons;
- Return.

Its governing reader route remains:

```text
prose
→ case card
→ state timeline
→ transition detail
→ probe
→ source ledger
→ claim ceiling
→ return to prose
```

This architecture works well when an object has already achieved enough stability to be represented as a Concept, Tool, Firewall, case structure, or comparator.

A new problem now appears.

FSP itself continues to generate open questions.

Recent examples include:

- Pattern of Discovery;
- Cross-Perspectival Calibration;
- Agency-Substrate Extraction;
- Temporal Interoperability;
- Repair Topology.

These are not merely unpublished Concepts.

They are **research programs**.

They arise because current FSP architecture exposes unresolved dependencies.

If the Encyclopedia has no place for such work, two bad outcomes are likely.

## Failure A — premature canonization

A provisional idea enters the public architecture as though it were already settled.

## Failure B — invisible development

Research remains outside the Encyclopedia until completed, hiding the provenance, alternatives, failures, and evidence by which canonical concepts actually develop.

FSP should avoid both.

The solution is a distinct epistemic layer:

> **Canonical FSP ≠ Research Frontier.**

---

# 2. The Encyclopedia's Epistemic Layers

The Encyclopedia should distinguish at least five statuses.

## 2.1 CANONICAL

A concept, grammar, Tool, Firewall, schema, or architecture that has passed the relevant FSP regression and is authorized for ordinary cross-domain use.

Examples may include:

- Map ≠ World ≠ Person;
- Tool ≠ Verdict;
- claim ceiling;
- remainder;
- translation ≠ identity;
- Generate ≠ Recommend ≠ Authorize;
- REOPEN;
- Return;
- current JTS grammar.

Canonical does not mean final.

> **Canonical ≠ unrevisable.**

It means:

> currently authorized as a stable shared FSP object.

---

## 2.2 COMPARATOR

An external or neighboring framework used to illuminate, pressure, extend, or criticize FSP.

Examples include:

- Brandom;
- Sebeok / Uexküll;
- Levin;
- Turner;
- phenomenology;
- pragmatism;
- capability theory;
- argumentation theory.

A comparator can generate revisions.

It is not thereby FSP doctrine.

> **Comparator fit ≠ canonical adoption.**

---

## 2.3 EXPERIMENTAL

A defined FSP object or implementation currently being tested.

Examples might include:

- a candidate formal schema;
- an executable probe;
- a new transition object;
- a provisional UI;
- a candidate Tool variant;
- a simulation;
- a domain-local workflow.

Experimental work normally has a narrower scope than a Research Frontier.

It answers:

> Does this proposed object work under specified conditions?

---

## 2.4 RESEARCH FRONTIER

An open research program created by an unresolved problem, tension, remainder, comparator pressure, empirical anomaly, or architectural limitation.

A Frontier may contain:

- hypotheses;
- candidate objects;
- cases;
- experiments;
- comparator studies;
- competing interpretations;
- candidate Firewalls;
- unresolved terminology.

Its defining feature is not immaturity.

It is explicit **openness of the question**.

> **Research Frontier ≠ weak version of Canonical Core.**

A Frontier is a different epistemic object.

---

## 2.5 DEPRECATED / SUPERSEDED

An earlier object that remains visible for provenance but is no longer recommended for current use.

Deprecated objects should preserve:

- former role;
- reason for supersession;
- successor object;
- historical dependencies;
- retained remainder.

> **Superseded ≠ erased.**

This matters because FSP itself is diachronic.

---

# 3. Epistemic Status Is Orthogonal to Importance

A Research Frontier may be philosophically more important than a small canonical Tool.

Status does not rank intellectual value.

It records **authorization state**.

Thus:

```text
importance
≠
maturity
≠
evidence strength
≠
canonical status
```

The Encyclopedia should never render "experimental" as "unimportant" or "canonical" as "true beyond revision."

---

# 4. Why the Frontier Is Part of FSP's Philosophy

The Research Frontier is not merely a website category.

It implements several FSP commitments.

## Provenance

Readers can see where an idea came from.

## Claim ceilings

The system displays what the current evidence does not yet establish.

## Remainder

Unresolved problems remain visible rather than being compressed away.

## REOPEN

Canonical architecture remains vulnerable to better evidence and stronger arguments.

## Return

Research must eventually return to the cases, users, or domains that motivated it.

Therefore:

> **Visible uncertainty is part of governed inquiry.**

# 5. The Frontier Card

Every Research Frontier should use a standardized card.

```text
RESEARCH FRONTIER
-----------------

ID
Title
Status
Opening problem
Why it matters
Trigger / provenance
Inherited FSP resources
Current hypothesis or question
Comparator traditions
Candidate cases
Candidate evidence
Candidate formal objects
Candidate Tools
Candidate Firewalls
Known alternatives
Known objections
Remainder
What would count as progress
What would weaken or falsify the current direction
Potential canonical impact
Claim ceiling
REOPEN conditions
Next tests
Version history
```

The card should remain intelligible to a public reader while supporting deeper research inspection.

---

# 6. Frontier Card: Opening Problem

Every Frontier begins with a problem rather than a proposed solution.

Example:

> **Pattern of Discovery:** Does mature FSP competence consist partly in transformed perceptual discrimination rather than continued explicit use of FSP vocabulary and procedures?

The Frontier should not begin:

> FSP requires a Pattern-of-Discovery module.

That would presuppose the answer.

So:

> **Research problem ≠ proposed architecture.**

---

# 7. Frontier Card: Trigger / Provenance

A Frontier must identify why it exists.

Possible triggers:

- unresolved remainder;
- comparator pressure;
- failed case;
- empirical anomaly;
- domain mismatch;
- older research residue;
- repeated workaround;
- student/user difficulty;
- conceptual contradiction;
- software limitation;
- new scientific development.

This field should cite the objects that generated the Frontier.

Example:

```text
Trigger:
Principia Agentialis pattern-of-discovery work
+
Tool-fading requirement
+
current Extended Critical Thinking architecture
```

This preserves developmental history.

---

# 8. Frontier Card: Inherited FSP Resources

Frontier work should not reinvent existing architecture unnecessarily.

Each Frontier must list relevant existing resources.

For example:

## Cross-Perspectival Calibration

Inherited resources:

- Map ≠ World ≠ Person;
- MY_MAP_OF_OTHER;
- translation governance;
- provenance;
- remainder;
- source ledger;
- claim ceiling;
- Sebeok Umwelt;
- Brandom attributed vs acknowledged commitment.

The research question then becomes:

> What additional structure is actually required?

rather than:

> What new vocabulary can we invent?

---

# 9. Frontier Card: Current Hypothesis

A Frontier may contain a current hypothesis.

But the wording must preserve its status.

Example:

> **Current hypothesis:** Some apparently conflicting evidence channels can be made mutually constraining through typed perspective and access records without reducing them to one latent variable.

Not:

> Cross-perspectival calibration is how first-person and third-person evidence work.

The hypothesis remains testable.

---

# 10. Frontier Card: Candidate Objects

A Frontier may propose formal objects.

Examples:

```text
PerspectiveEvidence
TemporalResponseWindow
AgencySubstrateIntervention
RepairTopology
PerceptualTransferRecord
```

Candidate objects should carry the label:

> **EXPERIMENTAL OBJECT**

until promoted.

They must not silently appear in canonical schemas.

---

# 11. Frontier Card: Candidate Firewalls

A Frontier may identify a recurring transition that appears to require protection.

Examples:

> **Boundary evidence ≠ reconstructible interior.**

> **Influencing choice ≠ altering capacity for choice.**

> **Repair ≠ preservation of existing structure.**

But a repeated phrase does not become a Firewall merely because it sounds useful.

Every candidate Firewall must remain marked:

> **CANDIDATE FIREWALL — NOT CANONICAL**

until it passes the Firewall consolidation process.

---

# 12. Firewall Consolidation

Before adding a new Firewall, the system must test whether it should be:

```text
ADD
MERGE
SUBTYPE
DOMAIN-LOCAL
REJECT
PENDING
```

Questions include:

- Is this transition already protected?
- Is the candidate merely an example?
- Is it domain-specific?
- Does it conflict with another Firewall?
- Is the stronger formulation actually supported?
- Does it help discriminate cases?
- Does it create unnecessary vocabulary?

> **New wording ≠ new Firewall.**

---

# 13. Frontier Card: Cases Before Canon

A Research Frontier should normally be tested against multiple cases before promotion.

The purpose is not numerical quota.

It is topology variation.

A candidate concept should survive cases that differ in:

- domain;
- scale;
- stakes;
- participant type;
- evidence structure;
- temporal pattern;
- normative pressure.

A concept that works only in the motivating case should normally remain domain-local.

> **Case fit ≠ portability.**

---

# 14. The Promotion-to-Core Gate

No Frontier object enters Canonical Core automatically.

The promotion route is:

```text
RESEARCH FRONTIER
↓
problem clarified
↓
cases developed
↓
comparator regression
↓
alternative explanations tested
↓
candidate object stabilized
↓
existing-Core collision test
↓
Firewall consolidation
↓
claim-ceiling audit
↓
projection / usability test
↓
domain-portability test where claimed
↓
ADD / MERGE / SUBTYPE / DOMAIN-LOCAL / REJECT / PENDING
↓
canonical change only if licensed
```

This is the **Promotion-to-Core Gate**.

---

# 15. Promotion Criterion 1 — Problem Persistence

The motivating problem must survive clarification.

Sometimes a Frontier disappears because the apparent problem was caused by:

- ambiguous terminology;
- missing documentation;
- UI failure;
- bad translation;
- an already existing Tool;
- a case-specific anomaly.

If the problem dissolves, no new canonical object is needed.

---

# 16. Promotion Criterion 2 — Distinctive Explanatory or Governance Value

The proposed object must add something.

Questions:

- Does it identify a failure current FSP misses?
- Does it improve claim discipline?
- Does it expose a hidden transition?
- Does it help cases become more inspectable?
- Does it improve translation?
- Does it reduce semantic drift?
- Does it improve Return?

If the object merely renames an existing distinction, merge or reject.

---

# 17. Promotion Criterion 3 — Comparator Regression

A candidate should be tested against strong neighboring traditions.

The purpose is not to prove novelty.

It is to avoid reinventing an established distinction badly.

Comparator outcomes may be:

- inherited;
- adapted;
- resisted;
- extended;
- unresolved.

The Encyclopedia should show this result.

---

# 18. Promotion Criterion 4 — Existing-Core Collision Test

Every proposed canonical addition must be tested against existing architecture.

Questions:

- Does it alter Map / World / Person?
- Does it change Tool / Verdict?
- Does it alter standing?
- Does it change JTS layers?
- Does it modify action states?
- Does it conflict with current normative-profile separation?
- Does it create an ontology claim?
- Does it change reader routing?

A proposed change must state which existing objects are affected.

> **Local success ≠ harmless global integration.**

---

# 19. Promotion Criterion 5 — Claim-Ceiling Audit

The candidate must carry a bounded claim.

Example:

Temporal Interoperability may support:

> participants operate under different observation and response windows that can affect coordination.

It may not yet support:

> FSP has discovered a universal temporal law of multi-agent systems.

The promotion decision must preserve the weaker licensed claim.

---

# 20. Promotion Criterion 6 — Usability / Projection Test

Canonical architecture must survive projection.

A concept that cannot be represented in:

- public Quick view;
- Standard explanation;
- Deep/Formal view;

without changing meaning may be too unstable.

Thus:

> **Progressive disclosure ≠ semantic mutation.**

Promotion requires a stable semantic core across depths.

---

# 21. Promotion Criterion 7 — Empirical or Case Burden

Not every canonical object requires experimental science.

But empirical claims require empirical evidence.

Historical claims require sources.

Formal claims require proof or clearly labeled conjecture.

Normative claims require explicit profile provenance.

Conceptual distinctions require discriminating cases.

The evidence burden must match the claim type.

---

# 22. Promotion Outcomes

The gate produces one of six statuses.

## ADD

New canonical object.

## MERGE

Useful content absorbed into an existing canonical object.

## SUBTYPE

Recognized as a structured specialization of an existing object.

## DOMAIN-LOCAL

Valid within a specific domain but not universalized.

## REJECT

Evidence or argument does not support adoption.

## PENDING

Promising, but unresolved.

This prevents "interesting" from becoming "canonical."

---

# 23. Rejection Is a Research Result

A Frontier that ends in REJECT has not failed.

It may establish:

- an attractive analogy does not travel;
- a distinction is redundant;
- a formalization adds no value;
- a case does not generalize;
- a comparator already handles the problem better.

The Encyclopedia should preserve rejected Frontiers when historically important.

> **Rejected hypothesis ≠ wasted inquiry.**

---

# 24. Cross-Linking Rules

Research Frontier pages should be integrated into the Encyclopedia graph without overwhelming the public surface.

The core rule is:

> **Frontiers attach to the objects that generate them.**

They should not initially compete with canonical navigation.

---

# 25. Cross-Link: Canonical Concept → Frontier

A canonical page may include:

> **Research Frontier**

when an unresolved question directly arises from the Concept.

Example:

```text
REMAINDER
└─ Cross-Perspectival Calibration
```

The link should communicate status.

Not:

> Learn more.

But:

> **Open research: Can heterogeneous evidence perspectives constrain one another without reduction?**

---

# 26. Cross-Link: Tool → Pattern of Discovery

Tools should eventually support:

```text
Tool
→ use
→ repeated application
→ transfer
→ scaffold fading
→ perceptual availability?
```

The question mark matters until evidence exists.

A Tool page should not claim that perceptual transformation occurs merely because that is the Frontier hypothesis.

---

# 27. Cross-Link: Failure Atlas → Agency-Substrate Extraction

Agency-Substrate Extraction initially belongs as a Frontier attached to relevant Failure Atlas entries.

Possible bridge:

```text
constraint
→ dependency
→ altered attention / evaluation / recovery capacity
→ possible substrate-level agency modification
```

This allows case accumulation before a universal concept is declared.

---

# 28. Cross-Link: State / Transition → Temporal Interoperability

Temporal Interoperability should attach to state/transition architecture.

Candidate questions:

- observation latency;
- decision frequency;
- authorization latency;
- effect latency;
- repair window;
- irreversible threshold;
- REOPEN window.

The current timeline remains canonical.

Temporal fields remain Frontier-level until cases show what the stable object should be.

---

# 29. Cross-Link: JTS Repair → Repair Topology

The current canonical JTS layer remains:

> **REPAIR**

The Frontier asks whether REPAIR needs explicit subtypes such as:

```text
repair within structure
redesign structure
refusal
exit
parallel institution
counter-institution
replacement / basin shift
```

Until tested:

> **Repair Topology ≠ revised canonical JTS grammar.**

---

# 30. Cross-Link: Translation / Remainder → Cross-Perspectival Calibration

This Frontier should attach strongly to:

- translation;
- remainder;
- source ledger;
- MY_MAP_OF_OTHER;
- phenomenal-node ecology;
- Umwelt;

It may eventually generate an Evidence Perspective object.

That remains provisional.

# 31. Public Navigation Rule

The public home page should not initially add five new top-level Frontier entrances.

This would confuse maturity with prominence.

Instead:

```text
Core / Domain page
↓
relevant object
↓
Research Frontier link
```

A separate Research Frontier index can exist for readers who deliberately want active research.

This preserves progressive disclosure.

The Encyclopedia should support a dedicated index:

Each entry displays:

- title;
- one-sentence problem;
- status;

- current phase;
- latest result;

Possible initial entries:

1. Pattern of Discovery
2. Cross-Perspectival Calibration
3. Agency-Substrate Extraction
4. Temporal Interoperability
5. Repair Topology

The index is not a roadmap promise.

It is a map of open inquiry.

---

# 33. Frontier Development Phases

A simple phase vocabulary:

```text
F0 — Problem registered
F1 — Provenance / comparator review
F2 — Case construction
F3 — Experimental / formal object
F4 — Adversarial regression
F5 — Promotion review
F6 — Closed: promoted / merged / local / rejected
```

Phase is not evidence strength.

It records workflow position.

---

# 34. Frontier Evidence States

Frontier cards may reuse the existing provenance ledger evidence vocabulary where useful:

- H — historical / philosophical recurrence
- C — conceptual reconstruction
- K — worked-case stress
- X — executable / formal implementation
- P — protocol-ready human test
- E — external empirical support

A Frontier can display multiple evidence states.

Example:

```text
Pattern of Discovery:
H / C strong
K emerging
P not yet frozen
E not established
```

This makes uncertainty inspectable.

---

# 35. Frontier Claim Ceilings

Every Frontier must state three things.

## Current supported claim

What can responsibly be said now?

## Not yet established

What stronger claim remains unsupported?

## Promotion-dependent claim

What could be licensed if specified tests succeed?

This prevents research prose from drifting into canonical language.

---

# 36. REOPEN at the Frontier Level

A Frontier is open by definition, but REOPEN still matters.

Why?

Because Frontiers can themselves sediment around early assumptions.

Each Frontier should specify triggers such as:

- case contradiction;
- comparator superiority;
- failed experiment;
- conceptual redundancy;
- new evidence;
- user burden;
- domain mismatch;
- formal inconsistency;
- ethical concern;
- better problem formulation.

REOPEN may change:

- the hypothesis;
- the object;
- the cases;
- the scope;
- the vocabulary;
- the Frontier itself.

---

# 37. REOPEN After Promotion

Promotion does not end REOPEN.

A canonical object should retain the Frontier provenance that produced it.

Thus:

```text
Frontier history
→ promotion decision
→ canonical version
→ later evidence
→ possible REOPEN
```

Readers should be able to inspect:

> Why is this canonical?

That is a core epistemic feature.

---

# 38. Deprecation and Historical Provenance

If a canonical object is later replaced:

```text
CANONICAL v1
↓
REOPEN
↓
revision / replacement
↓
DEPRECATED v1
CANONICAL v2
```

The old version should remain inspectable.

This enables historical reconstruction of FSP's own inquiry.

---

# 39. Frontier-to-Case Routing

A Research Frontier should not remain abstract.

Its reader route should be:

```text
Frontier problem
→ motivating case
→ current FSP handling
→ identified remainder
→ candidate extension
→ comparator
→ test / probe
→ current result
→ claim ceiling
→ promotion status
→ Return to Core
```

This parallels the canonical reader architecture while preserving the distinctive research role.

---

# 40. Frontier-to-Source Routing

Every significant historical, empirical, scientific, or philosophical claim should be source-bound where possible.

The Frontier page should distinguish:

- primary source;
- secondary interpretation;
- FSP reconstruction;
- hypothesis;
- inference.

This is especially important when older FSP work is being reconsidered.

> **Historical provenance ≠ current endorsement.**

---

# 41. Earlier Work as Frontier Provenance

Superseded FSP work should be treated as a legitimate research source.

For example, the earlier *Principia Agentialis* work may provide provenance for:

- Pattern of Discovery;
- first-/third-person bridge questions;
- OS1 privacy;
- coordination obstruction;
- temporal synchronization;
- Constructor Basin Escape;
- Dark Coherence;
- agency-substrate extraction.

The Encyclopedia should show:

```text
earlier formulation
→ identified limitation
→ retained problem
→ current Frontier
```

This is more informative than either restoring or forgetting the old architecture.

# 42. The Five Initial Frontiers

## RF-01 — Pattern of Discovery

**Problem:** Does mature FSP competence alter what a learner notices, rather than merely improving explicit procedural use?

Likely links:

- Critical Thinking;
- Tools;
- Attention;
- Authorial Capability;
- curriculum;
- scaffold fading.

---

## RF-02 — Cross-Perspectival Calibration

**Problem:** How can first-person, behavioral, relational, institutional, biological, and other evidence perspectives constrain one another without being reduced to one latent measure?

Likely links:

- Translation;
- Remainder;
- PRF;
- Umwelt;
- MY_MAP_OF_OTHER;
- source ledger.

---

## RF-03 — Agency-Substrate Extraction

**Problem:** When does influence over behavior become modification of the capacities by which an agent perceives, evaluates, chooses, resists, or recovers?

Likely links:

- Failure Atlas;
- capability;
- institutional amplification;
- AI;
- addiction;
- enhancement;
- coercion.

---

## RF-04 — Temporal Interoperability

**Problem:** How should FSP govern coordination among participants whose observation, action, authorization, consequence, and repair cycles operate at radically different rates?

Likely links:

- State;
- Transition;
- JTS;
- Asteria;
- AI;
- ecosystems;
- future generations.

---

## RF-05 — Repair Topology

**Problem:** When is responsible repair internal modification, structural redesign, refusal, exit, parallel construction, counter-institution, or replacement?

Likely links:

- JTS Repair;
- REOPEN;
- institutional sedimentation;
- counter-sedimentation;
- Constructor Basin Escape.

# 43. Frontiers Should Be Allowed to Split

A Frontier may reveal multiple distinct problems.

Example:

Cross-Perspectival Calibration might split into:

- human first-/third-person calibration;
- interspecies translation;
- historical trace reconstruction;
- AI attribution.

Splitting is not failure.

> **One motivating question ≠ one permanent research object.**

---

# 44. Frontiers Should Be Allowed to Merge

Conversely, two Frontiers may prove to be one problem.

For example:

Temporal Interoperability may become a subtype of Translation Governance.

Repair Topology may become a structured extension of JTS Repair rather than a separate canonical Concept.

The promotion process should prefer consolidation over vocabulary growth.

---

# 45. Frontier Governance and Standing

Who may change a Frontier?

Initially, contributors may propose:

- new evidence;
- cases;
- objections;
- candidate objects;
- revised hypotheses.

But canonical promotion requires explicit governance.

The Encyclopedia should distinguish:

- contribution standing;
- editorial standing;
- canonical authorization.

Thus:

> **Contribution ≠ canonical authorization.**

This is FSP self-governance applied directly.

---

# 46. No Automatic Promotion From Popularity

A Frontier may become widely used before it is well supported.

Therefore:

> **Adoption ≠ adequacy.**

And:

> **Popularity ≠ canonical status.**

The promotion gate remains evidence- and argument-sensitive.

---

# 47. No Automatic Rejection From Complexity

Some Frontiers may be mathematically, empirically, or philosophically difficult.

Difficulty alone does not justify removal.

The relevant question is whether the problem remains real and whether the Frontier formulation remains productive.

> **Unresolved ≠ useless.**

# 50. Why This Matters Philosophically

Traditional encyclopedias often present knowledge after stabilization.

The FSP Encyclopedia can do something additional.

It can make visible:

- what is currently stable;
- what remains uncertain;
- what problem generated the uncertainty;
- which alternatives are being considered;
- what evidence would matter;
- what could change the architecture.

This turns the Encyclopedia from a repository of conclusions into a **diachronic environment for governed inquiry**.

It does not merely display what FSP thinks.

It displays:

> **how FSP learns.**

# 51. Constitutional Firewalls for the Frontier Layer

The Research Frontier architecture introduces the following constitutional protections:

> **Canonical ≠ final.**

> **Research Frontier ≠ weak Canonical Core.**

> **Comparator fit ≠ canonical adoption.**

> **Experimental success ≠ canonical portability.**

> **Case fit ≠ portability.**

> **New wording ≠ new Firewall.**

> **Interesting ≠ canonical.**

> **Popularity ≠ adequacy.**

> **Contribution ≠ canonical authorization.**

> **Rejected hypothesis ≠ wasted inquiry.**

> **Historical provenance ≠ current endorsement.**

> **Unresolved ≠ useless.**

> **Promotion ≠ closure.**

Most of these are governance rules for the Encyclopedia rather than candidate domain Firewalls.

---

# 52. Claim Ceiling

This build establishes:

> **The FSP Encyclopedia can distinguish Canonical, Comparator, Experimental, Research Frontier, and Deprecated/Superseded objects and can govern movement among them through explicit provenance, testing, claim ceilings, promotion gates, and REOPEN.**

It does not establish:

- that the five initial Frontiers will generate canonical changes;
- that their current formulations are optimal;
- that every research problem needs a Frontier page;
- that every canonical object requires empirical validation;
- that formal promotion guarantees truth;
- that the current Encyclopedia implementation already supports all required UI behavior.

---

# 53. REOPEN Conditions

Reopen this architecture if:

- status labels confuse readers;
- Frontier material overwhelms the public reader;
- promotion becomes bureaucratically burdensome;
- research objects cannot be cleanly distinguished from Comparators or Experiments;
- domain-local research requires different governance;
- users infer that Canonical means final truth;
- contributors cannot understand promotion criteria;
- the five initial Frontiers expose missing status types;
- software implementation makes provenance or version transitions opaque;
- promotion decisions themselves lack legitimate standing.

---

# 54. Implementation Sequence

The recommended implementation order is deliberately bounded.

## Phase 1 — Schema

Create the Research Frontier object and index.

## Phase 2 — Seed

Add the five initial Frontiers as F0/F1 objects.

## Phase 3 — Cross-link

Attach each to its existing canonical parent objects.

## Phase 4 — Reader

Build a Frontier reader route:

```text
problem
→ provenance
→ current handling
→ remainder
→ hypothesis
→ case
→ test
→ claim ceiling
→ promotion status
→ return
```

## Phase 5 — Regression

Test that:

- canonical pages remain unchanged in meaning;
- public navigation remains simple;
- Frontier status is unmistakable;
- no candidate Firewall renders as canonical;
- return links preserve context.

Only after that should the five research programs be developed deeply.

---

# 55. Final Constitutional Statement

The FSP Encyclopedia should not display only finished maps.

Doing so would conceal the very process of inquiry that FSP is designed to govern.

But neither should provisional ideas flow directly into the shared grammar.

The Encyclopedia therefore needs two complementary capacities:

> **stability without closure**

and

> **openness without semantic drift.**

The Research Frontier provides the membrane between them.

It allows questions to remain visible without pretending that they are answers.

It allows old work to remain available without restoring superseded claims.

It allows comparators to exert pressure without becoming doctrine.

```text
problem
→ Frontier
→ provenance
→ comparator
→ case
→ experiment
→ adversarial test
→ claim ceiling
→ promotion gate
→ canonical change if licensed
→ REOPEN
```
