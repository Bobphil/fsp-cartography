# FSP-TRANSFORMATION-ARCHITECTURE-1

## Assembly-History-Dependent Capability, Structured Possibility Search, Task-Sequence Reachability, JTS/STAG Coordination, and Hypothesis-Generation Grammar

**Status:** RESEARCH ARCHITECTURE — VERSION 1  
**Role:** Establish a bounded forward research program for modeling transformation across persons, institutions, biological systems, and societies without collapsing feasibility, salience, strategy, legitimacy, or success into one another.  
**Primary purpose:** Connect assembly history, PRF, capability, structured search, task sequencing, JTS coordination, STAG reachability, hypothesis generation, sedimentation, REOPEN, and Return in one inspectable transformation grammar.  
**Primary claim ceiling:** This document defines a candidate transformation architecture and research program. It does not establish a universal dynamics of persons, institutions, societies, biological systems, or history; it does not assume that agents explicitly search complete state spaces; and it does not authorize optimization to substitute for normative judgment.

---

# 1. Opening Problem

FSP can already inspect:

- representations;
- evidence;
- warrants;
- perspectives;
- agency;
- capability;
- standing;
- authorization;
- institutional amplification;
- repair;
- REOPEN;
- Return.

A further question now becomes unavoidable:

> **How do historically assembled agents move from one bounded state to another, and how do their actions change what becomes possible next?**

This question appears in:

- learning;
- biological adaptation;
- scientific discovery;
- personal development;
- organizational change;
- political and institutional reform;
- technological development;
- collective action;
- long-horizon projects.

The architecture therefore needs to represent not only judgment about a present state, but **transformation among states**.

# 3. State Is Bounded

Let:

```text
S_t
```

represent a bounded description of a system at time `t`.

This does not mean the system is exhausted by the state representation.

> **State representation ≠ complete system.**

A state record may include only what is relevant to the present inquiry:

- capacities;
- constraints;
- resources;
- relationships;
- location in institutional structures;
- current commitments;
- available evidence;
- current risks;
- current task state.

The state is therefore purpose-relative and revisable.

---

# 4. Assembly History Enters the Transformation State

A present state does not always determine future transformation potential.

Two agents can appear similar now but differ because of:

- training;
- trauma;
- developmental history;
- prior regeneration;
- institutional experience;
- social relationships;
- accumulated trust;
- previous failures;
- learned routines;
- technological infrastructure;
- legal history.

Therefore:

> **Same present state ≠ same future possibility structure.**

A richer transformation record may be written:

```text
X_t = {
  currentState,
  assemblyHistory,
  currentPRF,
  capabilityProfile,
  constraintProfile,
  relationStructure,
  institutionalEmbedding,
  relevantTraces,
  claimCeiling
}
```

The architecture does not require all history to be stored.

It requires the possibility that **retained history matters**.

---

# 5. Assembly Trace

A candidate formal object is:

```text
AssemblyTrace = {
  event,
  inducedChange,
  persistence,
  decay,
  reinforcement,
  contextDependence,
  capabilityEffect,
  relationEffect,
  salienceEffect,
  reversibility,
  evidence,
  claimCeiling
}
```

This distinguishes:

> **Historical occurrence ≠ retained functional trace.**

An event can matter historically without remaining causally or functionally active now.

Conversely, a trace may persist after its originating event is no longer salient to the agent.

---

# 6. Capability Is Vector-Like, Not a Single Score

A system's capability should not be reduced to one scalar measure.

A useful representation is:

```text
C_t = {
  c1,
  c2,
  c3,
  ...
  cn
}
```

where each component represents capability in a relevant task space.

Examples:

- sensing;
- planning;
- inhibition;
- memory;
- communication;
- repair;
- coalition formation;
- resource acquisition;
- legal action;
- technical production;
- recovery.

Therefore:

> **Capability gain in one task space ≠ global capability gain.**

And:

> **Local adaptation ≠ global resilience.**

A transformation can increase some capabilities while decreasing others.

---

# 7. Transformation as Capability Redistribution

A transformation may be represented schematically as:

```text
C_t → C_t+1
```

where:

```text
ΔC = (+c_a, -c_b, +c_c, ...)
```

The architecture therefore asks:

- what capability was gained?
- what capability was lost?
- what became easier?
- what became harder?
- what future transitions were opened?
- what future transitions were closed?

This is especially important for adaptation, specialization, training, institutional reform, and technological change.

---

# 8. Possibility, Feasibility, Visibility, and Authorization

The architecture distinguishes at least six sets.

## 8.1 Possible

Transformations that are not ruled out by the bounded model.

## 8.2 Feasible

Transformations that can plausibly be achieved given current capacities, resources, constraints, and relations.

## 8.3 Visible / Salient

Transformations that the agent or group can currently notice, represent, or entertain from its PRF.

## 8.4 Selectable

Transformations that can actually be chosen under the current decision structure.

## 8.5 Authorized

Transformations that are legitimate under the relevant standing, authority, consent, and institutional constraints.

## 8.6 Implemented

Transformations actually attempted or enacted.

Thus:

> **Possible ≠ feasible ≠ visible ≠ selectable ≠ authorized ≠ implemented.**

This is a core transformation Firewall.

---

# 9. Accessible Possibility Set

Let:

```text
F(X_t)
```

denote the feasible transformation set under the current bounded state.

Let:

```text
A_i(X_t) ⊆ F(X_t)
```

denote the subset accessible or salient to agent `i`.

This does not imply that agents literally compute these sets.

The notation records a structural distinction:

> **Feasible transformation ≠ represented transformation.**

This distinction connects directly with PRF and Pattern of Discovery (RF-01).

---

# 10. PRF as a Transformation Filter

A PRF does more than organize what an agent believes.

It can alter what the agent notices as actionable.

Thus:

```text
world
↓
available relations
↓
assembly history
↓
PRF
↓
salience
↓
recognized affordances
↓
candidate transformations
```

A transformation may be objectively feasible while remaining invisible to the agent.

Therefore:

> **Unavailable-to-PRF ≠ impossible-in-world.**

This is one of the key reasons education, inquiry, translation, and collaboration can expand practical possibility.

---

# 11. Pattern of Discovery (RF-01) Connection

Pattern of Discovery (RF-01) asks whether mature learning changes what an agent spontaneously discriminates.

The Transformation Architecture gives this a formal target.

A successful educational intervention may change:

```text
A_i(X_t)
```

even if the external environment is unchanged.

Therefore:

> **Learning may transform the accessible possibility set.**

But this remains a Research Frontier claim until empirical transfer is demonstrated.

> **Instructional exposure ≠ demonstrated salience transformation.**

---

# 12. Structured Possibility Search

Many systems face possibility spaces too large for exhaustive search.

Examples include:

- biological adaptation;
- scientific hypothesis generation;
- career planning;
- organizational restructuring;
- technological design;
- coalition formation.

The architecture must therefore not assume:

```text
enumerate all possibilities
→ compare
→ choose optimum
```

Instead it permits multiple mechanisms:

- heuristics;
- attractor dynamics;
- learned priors;
- local search;
- distributed coordination;
- physical constraint;
- evolutionary structure;
- analogical transfer;
- generative models;
- latent-space navigation;
- social suggestion;
- institutional filtering;
- unknown mechanisms.

Therefore:

> **Successful navigation ≠ exhaustive search.**

And:

> **Observed solution-finding ≠ known search algorithm.**

---

# 13. Structured Possibility / Transformation Search Problem

The open research problem is:

> **How do agents at different scales locate viable transformations in very large possibility spaces, and what roles are played by substrate structure, prior assembly, salience, attractors, learned representations, physical constraints, social relations, and institutional organization?**

This problem is not yet assigned a new Frontier number.

It should remain a **Research Frontier remainder / candidate program** until its relation to Pattern of Discovery (RF-01), Cross-Perspectival Calibration (RF-02), Agency-Substrate Extraction (RF-03), Temporal Interoperability (RF-04), and Repair Topology (RF-05) is clearer.

---

# 14. Levin / Planaria as a Motivating Case

The planarian barium-adaptation work motivates, but does not prove, the architecture.

The relevant pattern is:

```text
novel perturbation
↓
severe failure
↓
biological reorganization
↓
new viable configuration
↓
history-dependent capability
```

The case raises:

- how the system navigates a large response space;
- whether prior regenerative history changes later capability;
- whether adaptation changes tradeoffs among capabilities;
- how retained traces persist or decay.

The architecture does not infer a specific search mechanism from the observed result.

> **Biological adaptation ≠ proof of Platonic-space access.**

Levin's Platonic-space proposal may be represented as a comparator hypothesis, not as FSP ontology.

---

# 15. Task-Sequence Reachability

Many important goals are not reachable by one action.

They require sequences:

```text
S_0
→ S_1
→ S_2
→ ...
→ S_n
```

Each transition may alter the next feasible set.

A task can therefore matter not because it directly achieves the final goal, but because it changes what can be done next.

> **Intermediate task value ≠ immediate goal completion.**

This is a central strategic principle.

---

# 16. Enabling Tasks

A task may be classified as:

- terminal;
- enabling;
- protective;
- exploratory;
- capacity-building;
- coalition-building;
- authorization-seeking;
- information-generating;
- repair-oriented;
- option-preserving.

An enabling task has value because it changes future reachability.

For example:

```text
gain skill
→ qualify for role
→ enter institution
→ build relationship
→ gain coordination capacity
→ unlock larger project
```

The architecture should make such dependency chains inspectable.

---

# 17. Task Dependency Graph

A candidate representation is:

```text
TaskGraph = {
  target,
  tasks,
  prerequisites,
  enablingRelations,
  blockingConstraints,
  requiredCapabilities,
  requiredActors,
  requiredAuthority,
  risks,
  branchPoints,
  failureRoutes,
  repairRoutes,
  reopenConditions
}
```

This is not automatically a recommendation engine.

> **Dependency map ≠ recommended strategy.**

Recommendation requires separate normative and practical judgment.

---

# 18. Reachability

Let:

```text
R(X_0)
```

represent states reachable from initial transformation state `X_0` under a specified model.

Reachability is conditional on:

- capabilities;
- resources;
- relations;
- institutions;
- time;
- task order;
- external responses;
- uncertainty.

Therefore:

> **Model-reachable ≠ guaranteed.**

And:

> **Reachable ≠ desirable.**

And:

> **Desirable ≠ authorized.**

---

# 19. Path Dependence

If:

```text
X_0 → X_1 → X_2
```

and:

```text
X_0 → Y_1 → Y_2
```

then the future reachable sets from `X_2` and `Y_2` may differ even if the states appear similar on some variables.

Therefore:

> **Endpoint similarity ≠ identical future reachability.**

This gives assembly history direct strategic significance.

---

# 20. Option Value

Some transformations should be evaluated partly by whether they preserve future options.

A task may:

- open paths;
- close paths;
- create lock-in;
- increase reversibility;
- reduce reversibility;
- preserve fallback routes.

Thus strategy should ask not only:

> Does this advance the target?

but also:

> **What future option structure does this create?**

This prevents narrow optimization against one target variable.

---

# 21. Lock-In

A transformation creates lock-in when later reversal becomes costly, unavailable, or institutionally blocked.

Candidate questions:

- Which alternatives disappear?
- Who bears the cost of reversal?
- Is the lock-in visible beforehand?
- Can REOPEN still operate?
- Does the institution preserve exit?

Therefore:

> **Short-term gain ≠ acceptable long-term lock-in.**

---

# 22. JTS as Reachability Expansion

A Joint Task Space can alter what is feasible.

For isolated agent `i`:

```text
R_i
```

may exclude a target that becomes reachable for a coordinated group:

```text
R_JTS
```

Thus:

> **Coordination can enlarge the reachable state space.**

A JTS can supply:

- complementary capabilities;
- pooled resources;
- distributed information;
- authority;
- trust;
- infrastructure;
- sequencing;
- redundancy.

But:

> **Expanded reachability ≠ legitimate coordination.**

Standing and authorization remain separate.

---

# 23. STAG

A **STAG** is a large coordinated target whose realization depends on contributions that are individually insufficient.

Examples can include:

- scientific institutions;
- public health systems;
- ecosystem restoration;
- educational reform;
- large knowledge infrastructures;
- durable social institutions.

A schematic condition is:

```text
Target ∉ R_i
```

for isolated participants, while:

```text
Target ∈ R_JTS
```

under an appropriately organized Joint Task Space.

This is a structural definition, not a moral endorsement.

> **Large coordinated target ≠ worthy STAG.**

---

# 24. STAG Governance

A coordinated project must therefore pass at least three distinct questions:

```text
POSSIBILITY
Can this be reached?

STRATEGY
What task sequence could make it reachable?

GOVERNANCE
Should this target and this route be authorized?
```

Optimization cannot answer all three.

> **Strategic efficiency ≠ legitimacy.**

> **Collective feasibility ≠ justified collective goal.**

> **Successful coordination ≠ justified coordination.**

---

# 25. Lifetime Contribution

Some STAGS exceed individual lifetimes.

FSP should therefore represent contribution without requiring individual completion.

A lifetime contribution may:

- build tools;
- create institutions;
- preserve knowledge;
- expand capabilities;
- train successors;
- establish evidence;
- reduce future coordination costs;
- create durable infrastructure.

Thus:

> **Contribution ≠ completion.**

This links STAGS to stewardship and Return.

---

# 26. Return as Successor Capability

Authorial Return can be extended without changing its core meaning.

A major question becomes:

> **What do I return to the world such that others can continue the Doing?**

This may include:

- knowledge;
- institutions;
- capabilities;
- tools;
- trustworthy records;
- open questions;
- repair routes;
- preserved options.

Return is therefore not merely retrospective reflection.

It can alter the assembly history available to future agents.

---

# 27. Hypothesis Generation

FSP should distinguish three functions:

```text
GOVERNANCE
What claims are licensed?

DIAGNOSIS
Where are the mismatches, hidden transitions, and remainders?

GENERATION
What hypotheses could explain them?
```

Hypothesis generation begins when expected structure fails.

---

# 28. Hypothesis-Generation Grammar

A candidate grammar is:

```text
1. Describe current state.
2. Record relevant assembly history.
3. Identify PRFs / perspectives / scales.
4. State expected transition.
5. Observe actual transition.
6. Locate mismatch or remainder.
7. Generate candidate mechanisms.
8. Derive discriminating consequences.
9. Identify evidence that would weaken each candidate.
10. Test.
11. Bound the judgment.
12. REOPEN.
```

This is not a universal scientific method.

It is a governance grammar for making generated hypotheses inspectable.

---

# 29. Remainder-to-Hypothesis Transition

A remainder is not automatically a hypothesis.

The transition is:

```text
REMAINDER
↓
possible explanatory dimensions
↓
candidate mechanisms
↓
hypotheses
↓
predicted discriminators
```

Therefore:

> **Unexplained remainder ≠ evidence for the preferred hypothesis.**

And:

> **Hypothesis generation ≠ hypothesis confirmation.**

---

# 30. Cross-Scale Hypothesis Generation

A problem observed at one scale may be explained at another.

Examples:

- behavioral pattern → neural constraint;
- neural adaptation → social stabilization;
- local incentive → institutional pattern;
- institutional pattern → individual capability restriction.

Therefore:

> **Scale of observation ≠ required scale of explanation.**

But cross-scale proposals must preserve the existing Firewall:

> **Cross-domain analogy ≠ causal derivation.**

---

# 31. Hypothesis Space Can Change

Scientific and practical inquiry may not merely select among fixed hypotheses.

Inquiry can alter what hypotheses are representable or salient.

Thus:

> **Hypothesis revision ≠ always probability revision within a fixed hypothesis set.**

A new Tool, concept, measurement, representation, or collaborator can enlarge the candidate hypothesis space.

This is one reason Pattern of Discovery (RF-01) and transformation search are connected.

---

# 32. Institutional Transformation

Institutions change feasible sets by:

- enabling;
- prohibiting;
- funding;
- credentialing;
- routing information;
- assigning authority;
- stabilizing routines;
- imposing costs;
- distributing risk.

Therefore an institution can be analyzed partly as a transformation operator on capability and reachability.

Candidate question:

> **What transformations does this institution make easier, harder, visible, invisible, authorized, or impossible—and for whom?**

This is diagnostic, not itself a verdict.

---

# 33. Institutional Sedimentation

Repeated successful or failed task sequences can become:

- routines;
- policies;
- infrastructures;
- expectations;
- role definitions;
- informal norms.

Thus:

```text
Doing
→ repeated pattern
→ sedimentation
→ changed institution
→ changed future feasible set
```

This is recursive.

Institutions are not only environments for transformation.

They are partly products of prior transformations.

# 35. Anti-Foundational Constraint

The Transformation Architecture must remain compatible with FSP's anti-foundational orientation.

No single representation is automatically privileged as the final transformation description.

Therefore:

- behavioral state may matter;
- first-person report may matter;
- biological state may matter;
- institutional state may matter;
- legal state may matter;
- network state may matter;
- formal state may matter.

Which representation is relevant depends on the inquiry.

> **Transformation model ≠ transformation itself.**

This is the governing meta-Firewall.

# 36. No Universal Objective Function

The architecture must not assume that all transformation problems reduce to maximizing a single objective.

Individuals and institutions may face:

- plural values;
- incompatible goods;
- standing constraints;
- rights;
- uncertainty;
- irreversibility;
- distributional conflict.

Therefore:

> **Formal optimization ≠ ethical authorization.**

And:

> **Single-objective improvement ≠ flourishing.**

# 43. Regression Invariants

The architecture passes only if the following remain true.

**T1 — Anti-foundational:** No state representation becomes the system itself.

**T2 — History-sensitive:** Assembly history may alter future capability without implying that all history is causally active.

**T3 — Capability pluralism:** Capability is not reduced to one scalar score.

**T4 — Search neutrality:** The architecture does not assume exhaustive, heuristic, Bayesian, attractor-based, Platonic, or any other single search mechanism.

**T5 — Salience separation:** Feasible possibilities may remain invisible to a PRF.

**T6 — Strategy separation:** Task dependencies do not themselves recommend a strategy.

**T7 — Normative separation:** Reachability does not determine legitimacy.

**T8 — Standing preservation:** Coordination does not erase standing.

**T9 — Authorization preservation:** Capability or benefit does not confer authority.

**T10 — JTS compatibility:** JTS may expand reachability without changing its current governance layers.

**T11 — STAG neutrality:** Large coordinated targets are not morally endorsed merely because they are large or feasible.

**T12 — Hypothesis discipline:** Generated hypotheses remain distinct from evidence and confirmation.

**T13 — Frontier discipline:** Pattern of Discovery (RF-01), Cross-Perspectival Calibration (RF-02), Agency-Substrate Extraction (RF-03), Temporal Interoperability (RF-04), and Repair Topology (RF-05) remain Research Frontiers.

**T14 — No universal objective:** The architecture does not define one universal optimization target.

**T15 — Return preservation:** Transformation returns to lived Doing rather than terminating in the model.

---

# 44. Failure Conditions

The architecture fails if it:

- treats a transformation model as exhaustive ontology;
- assumes visible possibilities equal feasible possibilities;
- treats successful adaptation as evidence for one preferred mechanism;
- interprets task graphs as automatic recommendations;
- optimizes a STAG without standing or authorization;
- treats capability gain as moral progress;
- erases path dependence;
- ignores lost capabilities or closed options;
- makes assembly history determinative;
- promotes a Research Frontier without the Promotion-to-Core Gate;
- turns Return into mere reporting rather than renewed Doing.
